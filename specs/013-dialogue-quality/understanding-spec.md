# Спека: переделка слоя понимания намерений (AutoMind chat)

Nov 26, 2026 · @Miguel — исходный документ владельца (вход спек 013 и 014), сохранён дословно 2026-11-26.

## 1. Контекст и проблема

Переделываем шаг, который решает, чего хочет человек: от входящего сообщения до выбора действия политикой. Сейчас этот шаг регулярно понимает намерение неправильно, и причина в дизайне, а не в отдельных багах.

Что делает шаг сейчас. Сообщение превращается в Interpretation: одна метка request из 14 значений, поле relation, список изменений карточки delta и язык. Затем код переписывает метку по ключевым словам. Политика (dialog/policy) смотрит на метку и на карточку и выбирает действие.

Почему ломается — пять причин:
- Проверки по спискам слов (phrases._YES, _NO, _CHOOSE, _GO) срабатывают раньше модели и перекрывают её ответ.
- Намерение разбирается в 4+ местах разными способами, метку пишут или переписывают 5–6 мест. Нельзя ответить, почему система решила именно так.
- У сообщения одна метка, хотя в живой речи бывает два намерения сразу. Метки смешивают цель, ответ на вопрос бота, реакцию на прошлый ответ и техническое происхождение.
- Пока у бота открыт вопрос, любое сообщение считается ответом на него. Вопрос пользователя теряется.
- Промпт interpreter.md — 166 строк, около 1900 слов правил-заплаток. Регрессионных тестов на понимание в архиве нет.

Примеры промахов (проверены по коду):

| Сообщение | Намерение человека | Что делает система | Где ломается |
|---|---|---|---|
| «да, но дизель» на карточку | согласен + смени двигатель | «да», дизель потерян | yes_or_no: фраза начинается с «да» |
| «давно хотел дизель» | новый факт | «да» | startswith("да") |
| «дайте подумать» | пауза | «да» | startswith("да") |
| «para mi familia» | «для моей семьи» | «нет» | para в списке _NO |
| «answer me about fuel» | вопрос | «нет / хватит» | answer в _NO |
| «все равно хочу дизель» | хочу дизель | «выбери сам» | choose_for_me перекрывает модель в apply |
| «do you have any…» | вопрос | «выбери сам» | фраза кончается на « any» |
| «давай сравним с BMW» при открытом вопросе о версии | добавить BMW | вероятно «выбери за меня», модель не вызвана | go_ahead + picked_option до модели |
| «а что такое DSG?» при вопросе о коробке | общий вопрос | засчитано как ответ, вопрос повторён | general_question → compare при открытом вопросе |
| «да, и добавь Hyundai» | два намерения | одно теряется | одна метка на сообщение |
| «переформулируйте» в русском чате | — | приходит по-английски | Reading(None, None, ask="rephrase"), сброс language="en" |

## 2. Цели и не-цели

Итог переделки: намерение понимается в одном месте, одной моделью, и каждое решение можно объяснить по одной записи.

Цели
1. Одна точка понимания текста. Любой текст пользователя разбирает один компонент, в том числе ответ на подтверждение.
2. Кнопки без угадывания. Кнопка шлёт идентификатор варианта, а не слово, которое потом сравнивают со списком.
3. Несколько намерений в одном сообщении: ответ на вопрос бота, новые цели и новые факты — отдельными полями.
4. Вопрос пользователя не теряется, когда у бота открыт свой вопрос: бот отвечает и повторяет свой вопрос.
5. Политика начинает с цели человека и объясняет, чего не хватает для неё.
6. Каждый ход оставляет одну запись: что сказала модель, что поправил код и почему, какое правило выбрало действие.
7. Изменения промпта и правил проверяются эталонным набором реплик до выката.

Не-цели
- Не передаём выбор действия модели. Действие по-прежнему выбирает код.
- Не меняем CaseDelta и доменную apply(): правила изменения карточки остаются.
- Не трогаем идентификацию, исследование, отчёт и guard.
- Не убираем проверки ответа модели кодом (числа есть в тексте, ключи машин существуют): они работают хорошо.

## 3. Текущее устройство: где понимается намерение

Намерение сейчас определяется в восьми местах кода. В новой схеме от них остаются два компонента: Understander и IntentResolver (раздел 5).

| Место | Что делает | Проблема | В новой схеме |
|---|---|---|---|
| InterpretationService.read, ветка car_edit | кнопка «Изменить» → delta кодом | любая ошибка → «какую машину?» | остаётся как структурное действие UiAction, с точными ошибками |
| read, ветка preset | кнопка сама называет запрос | запрос кнопки смешан с намерениями человека (rescore, report_saved) | UiAction, отдельный тип |
| read → picked_option | текст = предложенный вариант? (yes_or_no, choose_for_me, go_ahead) | до модели, ложные срабатывания | удаляется; кнопки шлют option_id, текст идёт в модель |
| read → interpret() | модель + проверки кодом | одна метка, перегруженный промпт, язык теряется при ошибке | Understander с новой схемой; проверки остаются |
| InterpretationService.apply | choose_for_me(text) переписывает метку модели; general_question → compare при открытом вопросе; страховочная сеть марок | решения о намерении спрятаны в применении изменений | apply только применяет изменения; решения — в IntentResolver |
| stages/understood.pending_answered | снимает открытый вопрос по метке | вопрос снимается всегда, даже если на него не ответили | по answer_to_pending; не отвечено → вопрос остаётся |
| nodes/confirm.apply_intake (и другие apply_*) | свой разбор текста: ≤ 3 слов без цифр → yes_or_no, иначе в interpret | «да, но дизель» = 3 слова → «да»; дубль _card_edit | текст всегда в Understander; apply_* получает готовый PendingAnswer |
| nodes/research.apply_limit | свой yes_or_no на «продолжить?» | те же ложные срабатывания | как у apply_intake |

Метку request_kind потом читают ещё в семи местах: политика (rules/answer, general, limits), understand.py, research.py, report_writer, report_followup, tracing, метрики.

## 4. Новая модель данных

Одна метка request заменяется на несколько независимых полей. Каждое отвечает на свой вопрос, и они не исключают друг друга.

| Вопрос | Поле | Откуда |
|---|---|---|
| Это ответ на вопрос бота? Какой? | answer_to_pending: PendingAnswer \| None | кнопка (option_id) или модель |
| Чего человек хочет добиться? | goals: list[Goal] | модель или кнопка |
| Как он отнёсся к прошлому ответу? | reaction: Reaction \| None | модель |
| Какие факты он сообщил? | case_changes: CaseDelta (без изменений) | модель или кнопка «Изменить» |
| На каком языке отвечать? | language | модель + гистерезис чата |

Схемы

```python
# что возвращает модель (structured output)
class PendingAnswer(BaseModel):
    pending_id: str                 # id открытого вопроса; код сверяет с case.pending.id
    kind: Literal["option", "value", "yes", "no", "choose_for_me"]
    option_id: str | None = None    # только из предложенных вариантов
    evidence: str                   # слова пользователя, из которых это следует

GoalKind = Literal["compare", "single", "follow_up", "change_priorities",
                   "research_more", "ask_general", "critique"]

class Goal(BaseModel):
    kind: GoalKind
    focus_cars: list[str] = []      # ключи car#N
    focus_areas: list[str] = []
    question: str | None = None     # для follow_up / ask_general: сам вопрос

Reaction = Literal["thanks", "complaint", "correction", "rephrase"]

class Understanding(BaseModel):
    language: str
    answer_to_pending: PendingAnswer | None = None
    goals: list[Goal] = []          # порядок = порядок в сообщении
    reaction: Reaction | None = None
    case_changes: CaseDelta = CaseDelta()
    persona_evidence: str | None = None
    constraints_evidence: list[str] = []

# что присылает кнопка (модель не вызывается)
class UiAction(BaseModel):
    kind: Literal["pick_option", "confirm", "decline", "choose_for_me",
                  "edit_car", "research_more", "panel_edit"]
    pending_id: str | None = None
    option_id: str | None = None
    car_key: str | None = None
    field: str | None = None
    value: str | None = None
    focus_cars: list[str] = []
    focus_areas: list[str] = []

# что получает политика — единственный вход
class Override(BaseModel):
    rule: str                       # имя правила резолвера
    field: str                      # что поменяло
    before: object
    after: object
    why: str

class Intent(BaseModel):
    source: Literal["text", "ui", "system"]
    language: str
    answer_to_pending: PendingAnswer | None
    goals: list[Goal]
    reaction: Reaction | None
    case_changes: CaseDelta
    overrides: list[Override] = []  # пусто = модель или кнопка приняты как есть
```

Требование к Pending. У открытого вопроса появляются id и список вариантов с option_id: `{"id": "q-17", "kind": "QUESTIONS", "options": [{"id": "car#1:gearbox:automatic", "label": "Автомат"}]}`. Эти же id уходят в кнопки UI и в промпт модели.

Соответствие старых меток новым полям

| Старый request | Новое представление |
|---|---|
| compare, single | Goal(kind="compare" / "single") |
| follow_up_question | Goal(kind="follow_up", question=…) |
| weights_change | Goal(kind="change_priorities") + case_changes |
| research_more | Goal(kind="research_more"); от кнопки — UiAction(kind="research_more") |
| critique | reaction="complaint" + Goal(kind="critique") |
| correction | reaction="correction" + case_changes |
| general_question | Goal(kind="ask_general", question=…) |
| chitchat | goals=[], пустые case_changes, без ответа на вопрос |
| confirm_yes / confirm_no | answer_to_pending.kind = "yes" / "no" |
| choose_for_me | answer_to_pending.kind = "choose_for_me" |
| rescore | UiAction(kind="panel_edit"), source="ui" |
| report_saved | source="system", не намерение человека |
| поле relation | удаляется, заменено reaction |

Как выглядят проблемные сообщения в новой схеме

| Сообщение | answer_to_pending | goals | case_changes |
|---|---|---|---|
| «да, но дизель» | yes | — | engine: diesel |
| «а что такое DSG?» | — | ask_general | — |
| «да, и добавь Hyundai» | yes | compare | add_cars: Hyundai |
| «давай сравним с BMW» | — | compare | add_cars: BMW |
| «все равно хочу дизель» | value (если спрашивали про двигатель) | — | engine: diesel |

## 5. Новый поток

Текст всегда идёт в модель, кнопки — сразу в резолвер, и только резолвер вправе менять понятое намерение.

### 5.1. Компоненты

| Компонент | Вход → выход | Что делает | Чего не делает |
|---|---|---|---|
| Understander | дело, открытый вопрос с вариантами, история, текст → Understanding | один вызов модели со structured output | не смотрит на ключевые слова, не меняет дело |
| validate_understanding | Understanding + дело → Understanding или Rejected(reason) | проверки из текущего interpret(): ключи машин, числа в тексте, доказательства персоны, парсер двигателя; новые: pending_id и option_id существуют | не угадывает смысл |
| IntentResolver | Understanding или UiAction + дело → Intent | единственное место поправок; каждая поправка пишется в overrides | не выбирает действие |
| apply_changes | Intent + дело → новое дело + журнал | domain.apply(case_changes), применение ответа на вопрос, факты из текста | не меняет намерение |
| policy | Intent + ситуация → Action | цель → чего не хватает → действие | не читает текст |

### 5.2. Правила IntentResolver

Правила — обычные функции в одном модуле, каждая с именем и тестом. Стартовый набор:
1. stale_pending: answer_to_pending.pending_id не совпадает с открытым вопросом → ответ отбрасывается, остальное сохраняется.
2. option_from_ui: UiAction(pick_option) → answer_to_pending.kind="option" с тем же option_id, source="ui".
3. no_goal_with_pending: целей нет, ответа на вопрос нет, но есть case_changes по теме вопроса → answer_to_pending.kind="value". Заменяет старое «при открытом вопросе всё — ответ».
4. cars_safety_net: модель не нашла машин, а в тексте есть марка из справочника → добавить машину. Переезжает из apply без изменений логики.
5. language_hysteresis: текущий stable_language; язык при отказе модели берётся из чата, не "en".

Удаляются как правила понимания: yes_or_no, choose_for_me, go_ahead, picked_option по тексту и правило «≤ 3 слова без цифр». Они остаются только в аварийном режиме, когда модель недоступна (раздел 9), и тогда срабатывают только на точное совпадение всей фразы.

### 5.3. Изменения в графе

- Узел interpret → understand: вызывает Understander, проверки и IntentResolver, пишет в состояние intent (dict из Intent.model_dump).
- Узел apply_delta → apply_changes: только применение, без переписывания метки.
- Узлы apply_* у подтверждений: текст не разбирают. Ответ текстом всегда идёт в understand; кнопка приходит как UiAction и применяется как сейчас.
- После understand с answer_to_pending для подтверждения роутер ведёт в соответствующий apply_* с готовым ответом.
- Pending получает id и options[].id; снимается только когда на него ответили или когда человек явно сменил тему (новая цель compare с другими машинами).
- PER_TURN_RESET обнуляет intent; язык не сбрасывается в "en", а берётся из прошлого хода.

### 5.4. Изменения в политике

Политика строит решение от цели, а не от анкеты.
1. Доступная цель без предусловий. ask_general, follow_up по уже собранным данным и goals=[] отвечаются сразу. Если открыт вопрос бота, ответ заканчивается повтором этого вопроса (новое действие ANSWER_AND_REASK).
2. Цель с предусловиями (compare, single, research_more). Правила intake / confirm / research остаются, но становятся проверками для этой цели. Вопрос бота содержит причину: «Чтобы сравнить, нужен год Prado».
3. Несколько целей. Сначала цели без предусловий (ответ в том же сообщении), потом первая цель с предусловиями.
4. Situation получает intent вместо request. Action.reason ссылается на цель и на правило.

## 6. Промпт интерпретатора

Новый промпт understander.md пишется заново, цель — не больше ~800 слов вместо текущих ~1900. Частные случаи уходят из правил в примеры и в описания полей схемы.

Структура
1. Роль (2–3 предложения): ты разбираешь сообщение, не отвечаешь пользователю и не решаешь, что делать.
2. Четыре вопроса по порядку, по одному блоку на поле: отвечает ли человек на открытый вопрос; чего он хочет (можно несколько целей); как он отнёсся к прошлому ответу; какие факты сообщил.
3. Правила фактов — коротко и один раз: только из последнего сообщения, числа с дословной цитатой, машины по ключам car#N, ничего не додумывать.
4. Примеры — 15–20 пар «сообщение + контекст → JSON» из эталонного набора (раздел 8), на трёх языках, включая все примеры из раздела 1.

Вход модели

```
CASE FILE:   компактный JSON дела (как сейчас)
PENDING:     {"id": "q-17", "question": "Какая коробка у Kia Sorento?",
              "options": [{"id": "car#1:gearbox:automatic", "label": "Автомат"},
                          {"id": "car#1:gearbox:manual", "label": "Механика"}]}
              или null
LAST ANSWER: краткая сводка прошлого ответа бота (для reaction)
HISTORY:     последние N реплик
MESSAGE:     текст пользователя
```

Что уходит из промпта: ссылки на спецификации (spec NNN, FR-NNN), правило «пока вопрос открыт, каждое сообщение — ответ», дублирующие друг друга правила про персону и профиль. Правила раскладки по полям CaseDelta (двигатель → engine_hint, комплектация → trim_hint) переезжают в description полей схемы.

## 7. Наблюдаемость: запись понимания хода

Каждый ход сохраняет одну запись turn_understanding, по которой можно восстановить всю цепочку «что сказал человек → что сделал бот».

| Поле | Содержимое |
|---|---|
| turn_id, chat_id | связь с ходом |
| input | текст или UiAction, открытый вопрос с его id |
| model_raw | JSON, который вернула модель, версия промпта, имя модели |
| rejected | что отбросили проверки и почему (например, «бюджет 50000 нет в тексте») |
| overrides | список поправок IntentResolver: правило, поле, до, после, причина |
| intent | итоговый Intent |
| policy_trail | какие правила политики проверялись, какое сработало, Action.reason |

Требования:
- Запись идёт через порт-репозиторий, а не прямой сессией БД как record_intake. Ошибка записи не роняет ход, но пишется в лог с chat_id и turn_id.
- Метрики Prometheus: доля ходов с overrides по имени правила; доля rejected; доля ходов, где открытый вопрос задан повторно.
- Сигнал качества из tracing.previous_signals берётся из intent.reaction этого хода — не из остатка состояния прошлого хода.
- Служебный эндпоинт или скрипт «показать понимание хода» по turn_id для разбора жалоб.

## 8. Тестирование и критерии приёмки

Переделка принимается по эталонному набору реплик, собранному до написания нового кода. Тот же набор прогоняется на старом коде — это точка отсчёта.

Эталонный набор
- 100–150 случаев в YAML: дело (или ссылка на фикстуру), открытый вопрос, история, сообщение, ожидаемый Intent (только значимые поля) и ожидаемое Action.kind.
- Источники: все примеры из раздела 1; реальные промахи из продакшена (чаты с reaction=complaint/rephrase); «золотые диалоги», упомянутые в промпте.
- Покрытие: ru / es / en примерно поровну; каждый вид открытого вопроса (QUESTIONS, CONFIRM_VARIANTS, CONFIRM_COST, CONFIRM_INTAKE, лимит исследования); сообщения с двумя намерениями; похожие на «да»/«нет», но не они.

Три уровня тестов

| Уровень | Что проверяет | Модель | Когда запускается |
|---|---|---|---|
| Юнит | validate_understanding, каждое правило IntentResolver, политика на готовом Intent | нет | каждый коммит |
| Эталонный (eval) | сообщение → Intent → Action.kind на всём наборе | настоящая | каждое изменение промпта, схемы или правил; ночью |
| Диалоговый | 10–15 многоходовых сценариев через весь граф с фейковыми портами | скриптованная | каждый коммит |

Критерии приёмки
- [ ] Все примеры из раздела 1 проходят.
- [ ] Точность answer_to_pending (есть / нет + вид) ≥ 97% на наборе.
- [ ] Точность набора целей ≥ 92%; итоговое Action.kind ≥ 95%.
- [ ] Ни одной регрессии против старого кода на случаях, где старый код прав.
- [ ] Задержка шага понимания p95 не хуже текущей более чем на 20%.
- [ ] Каждый ход оставляет запись turn_understanding.

Пороги точности — стартовые, уточняются после замера старого кода на наборе.

## 9. План миграции и риски

Переделка идёт в шесть этапов. Старый путь принимает решения, пока новый не докажет на эталоне и в тени, что не хуже.

Этап 1 даёт пользу сразу и не зависит от остальных: он убирает самые частые промахи из раздела 1 до большой переделки.

Совместимость checkpoint
- Состояние графа хранится в Postgres по thread_id = chat_id. Новые ключи (intent) добавляются, старые (interpretation, request_kind) читаются до этапа 4 и удаляются после.
- Имена узлов — часть сохранённого состояния. Ход, ждущий на wait_* в момент выката, должен продолжиться. Поэтому wait_* не переименовываем, а interpret и apply_delta остаются алиасами до этапа 4.
- Pending без id из старых версий дела получает id при чтении (валидатор Pydantic со стабильным хэшем содержимого).
- Старые клиенты, которые шлют кнопки словом, обслуживаются как текст: слово идёт в модель вместе со списком вариантов.

Риски

| Риск | Что делаем |
|---|---|
| Дороже и медленнее: модель теперь вызывается и на короткие ответы «да» | дешёвая быстрая модель для роли understander; для нажатий кнопок модель не вызывается вообще |
| Модель недоступна | аварийный режим: точное совпадение всей фразы со списком да/нет, иначе мягкое окончание «сервис перегружен» |
| Несколько целей усложняют политику | на этапах 3–4 политика берёт первую цель, остальные только пишутся в запись; полная поддержка — этап 5 |
| Регрессии в случаях, которые сейчас лечат заплатки в промпте | каждая заплатка из interpreter.md и списков слов превращается в случай эталонного набора до удаления |
| Код вне архива (delivery.web, клиент) зависит от preset и формата кнопок | перед этапом 2 проверить всех потребителей этого формата |

## 11. Контракт узлов графа

(Развёрнут в спеку `specs/014-node-contracts/`; ниже — исходный текст.)

У каждого узла появляются явные типизированные вход и выход. У каждой части состояния — один владелец. Нарушение контракта ловится сразу, с именем узла и ключа.

### 11.1. Что не так сейчас

| Проблема | Пример из кода |
|---|---|
| У типов выхода только 4 из ~30 узлов | ReadState, AppliedState, AssessedState, PolicyState; остальные возвращают dict[str, Any] |
| Вход узла нигде не описан | узел читает state.get("…") в любом месте своего кода |
| total=False везде | ни один ключ не обязателен, отсутствие незаметно |
| Один ключ пишут несколько узлов | request_kind — interpret и apply_delta; done, action, reply_text — почти любой |
| Ключи вне схемы | provider_down читается из итогового состояния, но в TurnState его нет |
| Ручной список сброса | PER_TURN_RESET забыл interpretation, и она утекает в следующий ход |
| Настройки узла — безымянный bool | ("interpret", interpret_node, True) — из кода не видно, что True = «ретраить при сбое провайдера» |
| Карточка читается из БД в каждом узле | load_case(c) в ~20 узлах, сохранение без проверки версии |

### 11.2. Состояние по разделам, у каждого раздела один владелец

Вместо плоских ~35 ключей — несколько разделов верхнего уровня. Писать в раздел может только его владелец.

| Раздел | Что в нём | Владелец | Живёт |
|---|---|---|---|
| chat | язык чата, fingerprint последнего отчёта | терминальные узлы (через reply) | весь чат |
| input | chat_id, turn_id, user_text, ui_action | раннер (до графа) | один ход |
| understanding | Intent или AskBack | understand | один ход |
| applied | новая версия карточки, журнал изменений, что не отвечено | apply_changes | один ход |
| assessment | состояние машин, план, стоимость, осуществимость | assess | один ход |
| decision | Action, счётчик проходов | policy | один ход |
| confirm | payload вопроса, ответ, флаги «одобрено / отказано» | узлы prepare_* / apply_* | один ход |
| research | задачи, раунд, лимиты, «исследование сделано» | узлы исследования | один ход |
| research_results | результаты параллельных задач (reducer «дописать») | research_job | один ход |
| notices | уведомления (reducer «дописать») | любой узел, только дописывание | один ход |
| reply | текст, блоки, action, fingerprint, outcome (в т.ч. provider_down) | терминальные узлы | один ход |

Сброс между ходами становится автоматическим: узел begin_turn ставит None во все разделы с пометкой «один ход». Ручного списка PER_TURN_RESET больше нет, и забыть ключ нельзя.

### 11.3. Узел с явным входом, выходом и следующим шагом

Узел записывается так, чтобы по его сигнатуре было видно всё: что читает, что пишет и куда может пойти дальше.

```python
class UnderstandIn(BaseModel):
    model_config = ConfigDict(frozen=True)
    input: TurnInput          # обязательно
    chat: ChatMemory          # обязательно

class UnderstandOut(BaseModel):
    model_config = ConfigDict(frozen=True, extra="forbid")
    understanding: Understood | AskBack

    def next(self) -> Literal["apply_changes", "reply"]:
        return "reply" if isinstance(self.understanding, AskBack) else "apply_changes"

@node("understand", reads=UnderstandIn, writes=UnderstandOut, retry=Retry.PROVIDER)
async def understand(inp: UnderstandIn, ctx: TurnContext) -> UnderstandOut:
    case = await ctx.case()   # карточка из кеша хода
    ...
    return UnderstandOut(understanding=intent)
```

Декоратор @node делает механику один раз для всех узлов:
1. Собирает UnderstandIn из состояния. Нет обязательного раздела → ContractError("understand: нет input"), а не тихий None.
2. Вызывает функцию с типизированными объектами: никаких state.get(...) и model_validate внутри узла.
3. Проверяет, что узел пишет только свои разделы (реестр владельцев из 11.2).
4. Превращает выход в JSON для checkpoint (model_dump) и возвращает LangGraph Command(update=…, goto=out.next()). Следующий шаг решает сам узел, отдельный роутер с флагом done не нужен.
5. Записывает узел в трассу (сейчас это делает traced).

Настройки узла — именованные, без безымянных bool: retry=Retry.PROVIDER | Retry.NONE. Узел с ретраем обязан быть без побочных эффектов до вызова модели: иначе ретрай повторит записи в БД, как сейчас в report и answer.

### 11.4. Карточка клиента — один раз за ход

- ctx.case() читает карточку из БД при первом обращении и держит в памяти до конца хода.
- ctx.save_case(case, changes) сохраняет с ожидаемой версией. Конфликт → VersionConflict, а не StoreUnavailable.
- После продолжения хода (Command(resume)) и после рестарта кеш пуст и читается заново: TurnContext создаётся на каждый ainvoke.

### 11.5. Контракт проверяется и документируется автоматически

- Тест на форму графа: для каждого узла и каждого обязательного раздела его входа на каждом пути от START есть узел-владелец, который его пишет.
- Тест владельцев: никакие два узла не пишут один раздел (кроме reducer-разделов notices, research_results).
- Команда python -m automind.chat.dialog.contract печатает таблицу «узел · читает · пишет · куда идёт» из типов. Документация всегда совпадает с кодом.
- В тестах нарушение контракта — ошибка. В продакшене на переходном этапе — запись в лог и метрика, потом тоже ошибка.

### 11.6. Порядок внедрения

1. Декоратор @node поверх текущих плоских ключей: у каждого узла описаны вход и выход, поведение не меняется. Это сразу найдёт ключи вроде provider_down.
2. ctx.case() вместо load_case в узлах.
3. Разделы состояния и автоматический сброс. Для старых checkpoint — чтение плоских ключей в переходном адаптере.
4. Command(goto=…) вместо роутеров с done. Политика остаётся роутером: её выбор — центр графа, его лучше видеть в graph.py.

Шаги 1–2 можно делать до переделки понимания (раздел 9), шаги 3–4 — вместе с этапом 3 переделки.
