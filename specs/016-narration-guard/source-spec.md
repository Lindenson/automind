# Спека: проверка текста модели (guard) — факты вместо чисел, утверждения вместо слов

Nov 27, 2026 · a teammate

## 1. Контекст и проблемы

Сейчас модель пишет числа сама, а dialog/guard.py пытается задним числом отличить правду от выдумки по регуляркам и спискам слов. Это принципиально ненадёжно: он и пропускает ошибки, и вырезает правильные фразы.

Как работает сейчас (report_writer.write_report):
1. Код считает facts и blocks, модель пишет текст по facts.
2. check_numbers: все числа из facts, blocks и карточки складываются в одно множество; предложение с числом вне множества (допуск 0,5%, кроме ALWAYS_OK = 0, 60, 62, 100, 200, 400) удаляется.
3. report_violations: четыре правила по спискам слов на ru / en / es (absence, sub_threshold, tie_winner, saving_costlier).
4. Нарушения → одно переписывание → если не помогло, предложения удаляются молча.

Прогон текущего кода (данные: Sorento 42 500 €, 6,6 л/100 км, 230 л.с., 2021 г.; Prado 38 900 €, 9,8 л, 204 л.с.; ничья; Sorento дороже за период):

| Текст модели | Результат | Ошибка guard |
|---|---|---|
| «2. Prado — 205 л.с.» (в данных 204) | оставлено | допуск 0,5% пропускает неверную цифру |
| «Sorento обходится на 400 € в год дешевле» | оставлено | 400 в ALWAYS_OK |
| «Sorento стоит 2021 евро в месяц» | оставлено | 2021 есть в данных как год — число без смысла и единиц |
| «Расход у Sorento около двенадцати литров» | оставлено | числа словами не проверяются |
| «Разница в цене — 3 600 €» (верно) | удалено | разности нет среди готовых чисел |
| «О надёжности Prado мы знаем мало» (данные есть) | не поймано | фразы нет в списке _ABSENCE |
| «Обе хороши, но я бы взял Prado» (ничья) | не поймано | фразы нет в _WINNER |
| «Sorento экономичнее в обслуживании» | ложно поймано | дешевле в обслуживании ≠ дешевле за период |

Корневые причины

| # | Причина | Следствие |
|---|---|---|
| R1 | Модель пишет числа сама | число нужно угадывать обратно из текста, с тремя форматами записи |
| R2 | Числа проверяются как мешок, без привязки к машине, показателю и единицам | любое совпадение числа = «правда» |
| R3 | Производные числа (разница, %, «в N раз») никто не считает | правильные сравнения вырезаются |
| R4 | Противоречия ищутся по словам, а не по смыслу | перефразировка обходит проверку; каждый промах лечится новым словом (следы: chat 5821ac77, reviewer 2026-11-03) |
| R5 | Исправление = молчаливое удаление | обрывки текста, пользователь не знает, что часть убрана |
| R6 | Предложения делятся по точке | «л.с.», «т.д.» режут предложение, удаляется кусок |
| R7 | Отчёт и короткий ответ проверяются по-разному | в ответе работает одно правило из четырёх |
| R8 | except Exception при переписывании | баги и исчерпанный бюджет молча превращаются в удаление текста |

## 2. Цели, не-цели, критерии

Главное изменение: модель больше не пишет числа и не делает непроверяемых утверждений. Она ссылается на факты по id и объявляет свои выводы структурно. Код подставляет числа и сверяет выводы с данными.

Цели
1. Выдумать число невозможно по построению. Каждое число в тексте происходит из факта с id или из производного значения, посчитанного кодом.
2. Сравнения разрешены и верны. Разница, процент, отношение доступны модели как операции над фактами.
3. Выводы проверяются по структуре. «Победитель», «дешевле», «нет данных» — это типизированные утверждения, и код сверяет их с вердиктом и таблицами независимо от языка и формулировки.
4. Проверка смысла поверх структуры. Независимый судья (модель) ищет необъявленные утверждения в тексте.
5. Исправление вместо удаления. Ошибка → точечное переписывание абзаца → если не вышло, шаблонная фраза из данных. Пользователь никогда не получает обрывков.
6. Один конвейер для всех текстов с данными: отчёт, ответ на уточнение, альтернативы.
7. Полный след. Каждая проверка и каждое исправление записаны и воспроизводимы.

Не-цели
- Не меняем расчёты отчёта (TCO, баллы, вердикт) — только то, как они попадают в текст.
- Не проверяем стиль и тон текста.
- Не рассчитываем на 100% гарантию от смысловых ошибок: числа гарантируются построением, выводы — проверкой с измеримой точностью.

Критерии приёмки

| Критерий | Сейчас | Цель |
|---|---|---|
| Выдуманные числа в итоговом тексте (атакующий набор) | 4 из 6 проходят (прогон из раздела 1) | 0 |
| Правильные сравнения, вырезанные проверкой | регулярно | 0 |
| Противоречия вердикту, пропущенные в итоге | неизвестно | ≤ 1% отчётов на эталонном наборе |
| Ложные срабатывания проверки выводов | неизвестно | ≤ 3% предложений |
| Тексты с обрывками после исправления | есть | 0 |
| Списки слов для поиска противоречий | 8 списков на 3 языках | 0 (остаётся только детектор чисел-словами) |
| Доп. стоимость на отчёт (судья) | 0 | ≤ 15% стоимости написания текста |

## 3. Архитектура

Код считает факты, модель пишет текст со ссылками на факты и списком своих выводов, код проверяет и подставляет числа, независимая модель-судья читает готовый текст.

| Компонент | Модуль | Работа | Детерминирован |
|---|---|---|---|
| FactSheetBuilder | narration/facts.py | Computed → FactSheet | да |
| Writer | narration/writer.py | FactSheet + запрос → WriterOutput | нет (LLM) |
| StructureCheck, BareNumberCheck, ClaimCheck | narration/checks.py | слои 1–3 | да |
| Renderer | narration/format.py | шаблоны → текст на языке пользователя | да |
| Judge | narration/judge.py | слой 4 | нет (LLM) |
| Repairer | narration/repair.py | лестница исправления | шаг 1 — LLM, шаги 2–3 — код |
| Narrator | narration/service.py | собирает конвейер, пишет NarrationLog | — |

Узлы графа (report, answer, alternatives) вызывают только Narrator.write(...). dialog/guard.py и проверки внутри report_writer.py удаляются на последнем шаге миграции.

## 4. Модель данных

Все типы — Pydantic, frozen, в новом пакете application/services/narration/. Факт знает свою машину, показатель, единицы и точность — именно этого не хватает сейчас (R2).

### 4.1. Факты

```python
class Unit(StrEnum):
    EUR = "eur"; EUR_PER_YEAR = "eur/year"; L_100KM = "l/100km"; KWH_100KM = "kwh/100km"
    HP = "hp"; KW = "kw"; NM = "nm"; SEC = "s"; KMH = "km/h"; KG = "kg"; LITRE = "l"
    MM = "mm"; KM = "km"; YEAR = "year"; YEARS = "years"; PERCENT = "%"; SCORE = "score"

class Fact(BaseModel):
    model_config = ConfigDict(frozen=True, extra="forbid")
    id: FactId                     # "car#1.price", "car#2.tco_period", "case.budget"
    subject: str                   # "car#1" | "case" | "verdict"
    metric: Metric                 # "price", "consumption", "max_power", "tco_period" …
    value: Decimal | int | str
    unit: Unit | None
    precision: Decimal             # шаг округления при показе: 100 €, 0.1 л, 1 л.с.
    source: Literal["catalogue", "research", "computed", "user"]
    confidence: Literal["high", "medium", "low"]

class FactSheet(BaseModel):
    """Всё, что писателю разрешено упомянуть. Строится из Computed отчёта."""
    model_config = ConfigDict(frozen=True)
    facts: Mapping[FactId, Fact]
    verdict: Verdict               # winner | tie, по каким критериям, порог различимости
    comparisons: Mapping[Metric, Comparison]   # кто лучше / ничья по каждому показателю
    gaps: frozenset[tuple[str, Metric]]        # (машина, показатель), по которым данных нет
    car_names: Mapping[str, str]               # "car#1" → "Kia Sorento"
```

Comparison хранит уже посчитанный вывод по показателю: better: str | None (ключ машины или None при ничьей), direction (больше лучше / меньше лучше), threshold. Именно с ним сверяются утверждения модели.

### 4.2. Плейсхолдеры

Модель пишет числа только так. Грамматика закрытая, новая операция = изменение спеки.

| Форма | Значение | Пример → текст (ru) |
|---|---|---|
| {fact:ID} | значение факта с единицами | {fact:car#1.price} → «42 500 €» |
| {diff:ID_A,ID_B} | абсолютная разница, без знака | {diff:car#1.price,car#2.price} → «3 600 €» |
| {pct:ID_A,ID_B} | на сколько процентов A отличается от B | → «9%» |
| {ratio:ID_A,ID_B} | во сколько раз | → «в 1,5 раза» |
| {sum:ID,ID,…} | сумма фактов одной единицы | → «4 300 €» |
| {name:car#N} | имя машины как в карточке | → «Kia Sorento» |

Правила валидности: id существует в FactSheet; у операндов одинаковый metric и единица (нельзя вычесть мощность из цены); pct и ratio запрещены для YEAR; деление на ноль — ошибка плейсхолдера.

### 4.3. Утверждения

```python
class ClaimKind(StrEnum):
    WINNER = "winner"            # «в целом лучше car#2»
    TIE = "tie"                  # «машины равны в целом»
    BETTER = "better"            # «car#1 лучше по metric»
    SAME = "same"                # «по metric одинаково»
    CHEAPER = "cheaper"          # «car#1 дешевле по metric» (price, tco_period, maintenance …)
    NO_DATA = "no_data"          # «по metric у car#N нет данных»
    RECOMMEND = "recommend"      # «советую car#N для …»

class Claim(BaseModel):
    model_config = ConfigDict(frozen=True, extra="forbid")
    kind: ClaimKind
    car: str | None              # car#N
    metric: Metric | None
    sentence_id: int             # к какому предложению относится

class Sentence(BaseModel):
    id: int
    paragraph: int
    template: str                # с плейсхолдерами

class WriterOutput(BaseModel):
    """Что возвращает модель-писатель (structured output)."""
    sentences: list[Sentence]
    claims: list[Claim]
```

Предложения сразу приходят разделёнными — вопрос «где конец предложения после «л.с.»» исчезает (R6). Claim связан с предложением по id, поэтому исправляется именно то предложение, чей вывод неверен.

## 5. Писатель

Модель-писатель получает FactSheet и возвращает WriterOutput через structured output. Свободный текст с числами она больше не пишет.

### 5.1. Что видит модель

Факты подаются таблицей с id, а не JSON-деревом: модели проще ссылаться на строку, чем искать путь в дереве.

```
FACTS
id                     car     metric          value    unit       confidence
car#1.price            Sorento price           42500    eur        high
car#2.price            Prado   price           38900    eur        high
car#1.consumption      Sorento consumption     6.6      l/100km    high
car#2.consumption      Prado   consumption     9.8      l/100km    medium
car#1.tco_period       Sorento tco_period      31800    eur        high
...
COMPARISONS
price        better=car#2   (lower is better)
consumption  better=car#1   (lower is better)
reliability  same           (difference below threshold)
VERDICT      tie
GAPS         car#2.reliability
```

### 5.2. Что модель возвращает

```json
{
  "sentences": [
    {"id": 1, "paragraph": 1,
     "template": "{name:car#2} дешевле при покупке на {diff:car#1.price,car#2.price}."},
    {"id": 2, "paragraph": 1,
     "template": "Зато {name:car#1} расходует {fact:car#1.consumption} против {fact:car#2.consumption}."},
    {"id": 3, "paragraph": 2,
     "template": "В целом машины равны: выбор зависит от того, что для вас важнее."}
  ],
  "claims": [
    {"kind": "cheaper", "car": "car#2", "metric": "price", "sentence_id": 1},
    {"kind": "better",  "car": "car#1", "metric": "consumption", "sentence_id": 2},
    {"kind": "tie",     "car": null,    "metric": null, "sentence_id": 3}
  ]
}
```

### 5.3. Правила в промпте (кратко)

1. Любое число — только плейсхолдером. Не пиши цифры и числа словами («двенадцать», «вдвое»).
2. Каждый вывод «лучше / дешевле / победитель / ничья / нет данных / советую» объяви в claims.
3. Машины называй через {name:car#N}.
4. Одно предложение = один элемент sentences.

Правила стиля, персоны и структуры отчёта остаются в текущих промптах reporter_* и answerer.

### 5.4. Кто пользуется

Один конвейер Narrator.write(kind, fact_sheet, request, lang) для трёх текстов: kind = report | answer | alternatives. Сейчас у каждого свой набор проверок (R7). general_node (общие вопросы без данных о машинах) остаётся свободным текстом, но с правилом «без цифр о конкретных моделях» и слоем 2 проверки из раздела 6.

## 6. Проверки

Четыре слоя, от дешёвых и точных к дорогим и вероятностным. Первые три — детерминированный код без списков слов о смысле; четвёртый — независимая модель-судья.

| Слой | Что проверяет | Ловит из раздела 1 | Цена |
|---|---|---|---|
| 1. Структура | плейсхолдеры валидны: id существуют, единицы совпадают, операции допустимы; claims ссылаются на существующие предложения, машины и показатели | операции над разными единицами (разница цены и года), ссылки на несуществующие факты | ~0 |
| 2. Голые числа | в тексте вне плейсхолдеров нет цифр и числительных | «205 л.с.», «400 €», «двенадцати литров» | ~0 |
| 3. Утверждения против данных | каждый Claim согласуется с verdict, comparisons, gaps | «данных нет» при наличии; победитель при ничьей; «дешевле за период» у более дорогой | ~0 |
| 4. Судья | в готовом тексте нет необъявленных или неподтверждённых выводов | «я бы взял Prado» без Claim; «знаем мало»; год вписан в фразу о цене («стоит 2021 евро») | один дешёвый вызов модели |

### 6.1. Слой 2: голые числа

- Из шаблона вырезаются плейсхолдеры и имена машин/версий из FactSheet («Land Cruiser J250», «i30»). Исключения берутся из данных, а не угадываются регуляркой «перед цифрой буква».
- В остатке любая цифра = нарушение. Никаких ALWAYS_OK и допусков: «0–100 км/ч» — это часть названия метрики, и её подставляет рендерер ({fact:car#1.accel_0_100} → «разгон 0–100 км/ч за 8,2 с»).
- Числительные словами ищутся по закрытому словарю числительных ru / en / es («два»…«тысяча», «вдвое», «половина», «double», «doble»). Это единственный оставшийся список слов: словарь числительных конечен и не зависит от формулировок. Исключения вроде «одна из машин» — в словаре допустимых оборотов.

### 6.2. Слой 3: утверждения против данных

| Claim | Допустим, если |
|---|---|
| WINNER(car) | verdict.winner == car |
| TIE | verdict.tie |
| BETTER(car, metric) | comparisons[metric].better == car |
| SAME(metric) | comparisons[metric].better is None |
| CHEAPER(car, metric) | metric — денежная и comparisons[metric].better == car. «Дешевле в обслуживании» проверяется по maintenance, а не по tco_period — ложное срабатывание из раздела 1 уходит |
| NO_DATA(car, metric) | (car, metric) in gaps |
| RECOMMEND(car) | не ничья и verdict.winner == car; при ничьей — только с полем condition («если важнее расход»), и condition.metric согласуется с comparisons |

Дополнительная сверка чисел и выводов: если в предложении с CHEAPER(car#2, price) стоит {diff:car#1.price,car#2.price}, код проверяет знак разницы. «car#2 дешевле на X», когда car#2 дороже, — нарушение.

### 6.3. Слой 4: судья

- Вход: готовый текст (после рендеринга), FactSheet, список объявленных claims.
- Вопрос судье: «Для каждого предложения: есть ли в нём вывод о машинах, которого нет в claims, или который противоречит фактам?» Ответ — структура [{sentence_id, problem, explanation}].
- Судья — отдельная роль (judge) и другая дешёвая модель, не та, что писала текст: модель хуже ловит свои ошибки.
- Когда запускается: всегда для report; для answer — если в ответе упомянуто больше одной машины или есть claims.
- Судья не проверяет числа: они уже гарантированы слоями 1–2. Это сужает его задачу и повышает точность.
- Сбой судьи (провайдер недоступен) не блокирует ответ: текст уже прошёл слои 1–3. Событие пишется как judge_skipped.

## 7. Рендеринг чисел

Числа в текст подставляет код, одним форматтером для текста, таблиц и карточек. Одно и то же значение везде выглядит одинаково.

- Одна функция: render(value, unit, precision, lang) -> str в application/services/narration/format.py. Использует Babel (format_decimal, format_currency) с локалями ru, es, en. Сейчас форматирование разбросано по report_text и блокам.
- Округление по факту: precision задаёт тот, кто создал факт. Цена — до 100 €, расход — до 0,1 л, мощность — до 1 л.с. У производных операций точность берётся наихудшая из операндов; pct — до целого процента, ratio — до 0,1.
- Нечестная точность запрещена: факт с confidence = low рендерится с маркером «около» / «≈», который добавляет рендерер, а не модель.
- Направление в тексте, не в числе: diff всегда без знака. «Дороже / дешевле» пишет модель, а слой 3 проверяет, что направление совпадает с данными.
- Единицы и подписи метрик — из словаря на трёх языках: «л/100 км», «l/100 km»; «разгон 0–100 км/ч», «0–100 km/h».

Пример:

| Факт / операция | ru | es | en |
|---|---|---|---|
| car#1.price = 42500, precision 100 | 42 500 € | 42.500 € | €42,500 |
| car#1.consumption = 6.6 | 6,6 л/100 км | 6,6 l/100 km | 6.6 l/100 km |
| diff(price) = 3600 | 3 600 € | 3.600 € | €3,600 |
| ratio(consumption) = 1.48 | в 1,5 раза | 1,5 veces | 1.5 times |
| car#2.reliability_score = 7.2, confidence low | около 7,2 из 10 | unos 7,2 de 10 | about 7.2 out of 10 |

## 8. Исправление ошибок

Ошибка исправляется там, где она есть, и никогда не вырезается молча. На каждый текст — не больше одного цикла переписывания, затем детерминированная замена.

Лестница исправления
1. Точечное переписывание абзаца. Модель получает только абзац с нарушениями, список нарушений с причинами из проверки и нужные факты (например, «предложение 4: CHEAPER(car#1, tco_period), но comparisons.tco_period.better = car#2»). Остальные абзацы не трогаются — исправление не ломает уже проверенный текст. Переписанный абзац снова проходит слои 1–3 (судья второй раз не запускается).
2. Шаблонная замена. Если после переписывания нарушение осталось, предложение заменяется правильным фактом из данных по фиксированному шаблону из report_text — например, «За 5 лет с учётом потери стоимости Prado обойдётся дешевле на 1 200 €». Для каждого ClaimKind есть шаблон на трёх языках.
3. Удаление с пометкой — только если для предложения нет Claim (судья нашёл необъявленный вывод, а переписывание не помогло). Абзац собирается заново из оставшихся предложений (они целые, потому что пришли разделёнными), а в конце отчёта появляется неброская пометка «Часть выводов убрана: они не подтверждаются данными».

Сбои при исправлении

| Сбой | Реакция |
|---|---|
| Временная ошибка провайдера | сразу шаг 2 (шаблон), без повтора |
| BudgetExceeded | шаг 2; исключение не глотается и попадает в запись проверки |
| Переписанный абзац не прошёл слой 1 (битые плейсхолдеры) | шаг 2 для всех предложений абзаца с нарушениями |
| Баг в проверке или рендерере | исключение пробрасывается: ход FAILED. Никаких except Exception (R8) |

Если модель вернула невалидный WriterOutput (схема не совпала): один повтор с ошибкой валидации в промпте; затем — отчёт только из блоков и шаблонного вердикта, без текста модели, с пометкой.

## 9. Наблюдаемость

По любому тексту можно увидеть, что написала модель, что нашла каждая проверка и что изменило исправление. Сейчас пишется только число удалённых предложений (log_removed).

Запись проверки — одна строка в narration_checks на текст, через порт NarrationLog:

| Поле | Содержимое |
|---|---|
| turn_id, kind | ход и вид текста (report / answer / alternatives) |
| fact_sheet_hash | хэш FactSheet; сам лист фактов — в таблице по хэшу (расчёты уже сохраняются через persist_computations) |
| writer_output | WriterOutput целиком: шаблоны и claims |
| findings | [{layer, sentence_id, rule, detail}] по всем четырём слоям |
| repairs | [{sentence_id, step: rewrite / template / removed, before, after}] |
| judge | модель, результат или skipped с причиной |
| final_text | то, что увидел пользователь |
| prompt_version, writer_model, judge_model | чтобы сравнивать версии |

Метрики Prometheus
- narration_findings_total{layer, rule, kind} — сколько нарушений и каких. Рост после смены модели или промпта виден сразу.
- narration_repairs_total{step} — доля текстов, дошедших до шаблона и до удаления.
- narration_judge_disagreement_total — судья нашёл то, чего не нашли слои 1–3. Это сигнал, какой ClaimKind или правило промпта не хватает.
- narration_cost_eur{kind, stage} — стоимость написания, проверки судьёй и исправления отдельно.

Связь с обратной связью: если следующий ход — жалоба или исправление (OutcomeRecorder уже пишет такой сигнал), запись проверки этого текста помечается и попадает в очередь на разбор — кандидат в атакующий набор (раздел 10).

## 10. Тестирование

Слои 1–3 и рендерер тестируются без модели: на вход идёт готовый WriterOutput. Писатель и судья оцениваются на наборах с настоящей моделью.

| Набор | Что внутри | Что проверяем | Когда |
|---|---|---|---|
| Юнит-тесты слоёв 1–3 | ручные WriterOutput на каждое правило: валидный и нарушающий вариант | нарушение найдено и только оно | каждый коммит |
| Рендерер | таблица «факт × язык → строка», включая примеры из раздела 7 | точное совпадение строки | каждый коммит |
| Свойства (Hypothesis) | случайные FactSheet + случайные валидные шаблоны | в выходе рендерера каждое число равно округлённому факту или операции; исправление никогда не оставляет пустых абзацев | каждый коммит |
| Атакующий набор | 100+ случаев: все примеры из раздела 1, числа словами, год как цена, победитель при ничьей в разных формулировках, «дешевле» по разным метрикам; ru / es / en | в итоговом тексте 0 выдуманных чисел и ≤ 1% пропущенных противоречий | каждое изменение промпта или модели; ночью |
| Судья | размеченные вручную тексты: предложение → «есть необъявленный вывод / нет» | precision ≥ 0,9, recall ≥ 0,85 | при смене модели судьи |
| Эталонные отчёты | 20–30 реальных сравнений из продакшена (narration_checks → фикстура) | нет нарушений слоёв 1–3; полнота: вердикт и ключевые сравнения есть в тексте | ночью |

Критерии приёмки перед переключением
- [ ] Все 8 случаев из раздела 1 обрабатываются правильно.
- [ ] Атакующий набор: 0 выдуманных чисел, ≤ 1% пропущенных противоречий, ≤ 3% ложных срабатываний.
- [ ] Доля текстов, дошедших до шаблона или удаления, ≤ 5% на эталонных отчётах.
- [ ] Слепое сравнение читаемости старых и новых отчётов на 20 парах: новые не хуже в ≥ 80% пар.
- [ ] p95 времени написания отчёта растёт не больше чем на 25%; стоимость — не больше чем на 15%.

## 11. План миграции и риски

Пять шагов. Старый guard.py работает до шага 4 включительно и удаляется только после переключения всех видов текста.
1. Быстрые исправления в старом коде (не зависят от остальных): убрать ALWAYS_OK, допуск сделать абсолютным по округлению вместо 0,5%, except Exception → только временные ошибки провайдера, пометка пользователю при удалении, одинаковые проверки для отчёта и ответа. Проверка: атакующий набор на старом и исправленном коде.
2. FactSheet и рендерер. Сборка FactSheet из Computed отчёта, единый render(); блоки UI переходят на него. Текст модели пока старый.
3. Новый писатель + слои 1–3 в тени. На части ходов пишутся оба текста, показывается старый, новый пишется в narration_checks. Стоимость теневого режима ограничена долей ходов (например, 10%).
4. Судья и лестница исправления. Оценка судьи на размеченном наборе, затем включение в теневом режиме.
5. Переключение по видам текста: сначала answer, потом report, потом alternatives. После всех трёх — удаление guard.check_numbers, report_violations и списков слов.

Риски

| Риск | Что делаем |
|---|---|
| Текст с плейсхолдерами звучит деревянно (склонения в русском: «на 3 600 €», «в 1,5 раза») | рендерер знает формы единиц для чисел (pymorphy3 для ru); слепое сравнение читаемости в критериях приёмки |
| Модель плохо следует грамматике плейсхолдеров | structured output + примеры в промпте; метрика нарушений слоя 1 в теневом режиме |
| Модель занижает claims (не объявляет выводы), чтобы не попасть на проверку | именно это ловит судья; метрика narration_judge_disagreement_total |
| Судья добавляет задержку | дешёвая быстрая модель; запуск сразу после рендеринга; лимит времени, при превышении — judge_skipped |
| Фактов в Computed недостаточно для живого текста | на шаге 2 инвентаризация: какие числа сейчас встречаются в отчётах (по логам), и для каждого — факт или операция |
