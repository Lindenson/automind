# ADR-027: The profile drives the assessment: basis, weight breakdown, RESCORE, learned sources, intake by code

**Status**: Accepted · 2026-11-03 (spec 007, PRs #14–#24)

## Decision

1. **Profile basis.** Every profile field records how it is known:
   - `STATED`: the user said it;
   - `INFERRED`: taken from the user's words, which are kept in `profile.evidence`;
   - `ASSUMED`: a default from `config/profile_defaults.yaml`.

   Precedence is STATED > INFERRED > ASSUMED, and a weaker basis never overwrites a stronger one. Only non-ASSUMED fields move the weights. An INFERRED field that decides the winner (`ask_value.inferred_flip`) is shown as an assumption in the verdict, and a CONFIRM_PROFILE question is asked once per chat.
2. **Weight breakdown.** The criterion weights are computed in code from `config/profile_rules.yaml`, per rule. Each reason is shown (`family.FAMILY +10`, `priority.MEDIUM +20`). Manual weights are adjustments in points on top of the automatic ones, so they no longer freeze. An excluded criterion stays at 0.
3. **RESCORE.** The fingerprint is split into data (cars, variants) and parameters (profile, weights, period, km, limits).
   - An edit in the case panel changes only the parameters. It recomputes the scores, the cost, the verdict and a short "what changed" text from validated data, with no search and no interpreter.
   - The edit is stored with the hidden role `edit`.
   - The edit is saved under the turn-start advisory lock with a version check (`if_version`, 409 `version_conflict`).
   - An edit made during a turn is queued per chat. One worker merges the queued edits and applies them after the turn. A failure reaches the chat (`rescore_failed`).
4. **Verdict per profile.** The ownership cost covers the user's period and annual km, with a depreciation item. The rules for limits:
   - Over budget or over the monthly limit: a close in-limit runner-up becomes the pick; otherwise the headline says "best if the budget allows". When every car is over, the ranking stands.
   - A payback beyond 15 years is "does not pay back".
   - Another persona's different winner from the same data is shown.
5. **Learned sources.** A domain that yields accepted values for a market and area is learned and searched with a short query.
   - Only search hits count, so a URL the user sent never counts.
   - An acceptance that came through the domain's own learned query is neutral, so a domain cannot reinforce itself.
   - Empty results are cached briefly, not for the full TTL.
6. **The intake is answered by code where it can be.** A reply equal to an offered option (a tapped chip) is applied without the interpreter (`intake.pick`). Its variant, model or engine replaces the hints left by earlier options. Further rules:
   - A gearbox question offers gearboxes.
   - A new car bought now is the generation on sale.
   - The resolver never stamps the current generation on an older engine, and never stores a version without an engine.
   - A car added later inherits the shared condition and year.
7. **Robustness.**
   - A hop counter ends a looping turn with a report from the data at hand.
   - LLM nodes retry transient provider errors (`RetryPolicy`, 2 attempts) and then give a plain localized message.
   - A timeout after research was saved starts a hidden `report_saved` turn.
   - Pages are fetched only from public addresses, checked after DNS resolution and on every redirect (SSRF guard).
8. **Advice without named cars.** A need and a budget without a car select 2–3 candidates through the port `models_on_sale` (the cached line-ups and the catalog, no new search). The cars then go through the usual card, which is always shown for candidates.

## Consequences

The same data gives different, explained verdicts for different people. Panel edits are instant and never lost while the server runs; the queue is in memory, so an edit waiting during a restart is lost. Candidate quality depends on how many makes have a cached line-up.
